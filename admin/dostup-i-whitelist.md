# Доступ и SpringAuth v2

SpringAuth v2 — серверная авторизация для сети в `offline-mode`. Она работает
с официальными и неофициальными аккаунтами, любыми лаунчерами и не требует
клиентского мода.

{% hint style="warning" %}
До завершения приёмочных тестов v2 не заменяет работающий вход. Старый код
сохранён в `legacy/access-v1-kick/`; порядок безопасного перехода описан в
`spring-auth/docs/migration.md`.
{% endhint %}

## Компоненты

- публичный Velocity принимает игроков и назначает постоянный внутренний UUID;
- виртуальный Limbo внутри Velocity изолирует игрока до подтверждения входа;
- приватный Paper `main` проверяет локальный UUID-список;
- Access API на `springrp.ru/spring-auth/` хранит проходки, привязки и коды;
- Discord-приложение выполняет `/claim`, `/code` и синхронизирует роль/ник;
- главный Paper получает список разрешённых UUID из API по исходящему HTTPS.

Paper работает с `online-mode=false` и Modern Forwarding. Его игровой порт не
должен быть доступен извне: разрешено только подключение Velocity. RCON не нужен.

## Выдача проходки

Команда выполняется в консоли Velocity или доверенным администратором с правом
`springauth.admin`:

```text
/springauth grant <ник> <срок>
```

Примеры сроков: `12h`, `30d`, `4w`, `permanent`. Команда:

1. создаёт или продлевает проходку;
2. сохраняет постоянный случайный Minecraft UUID аккаунта;
3. добавляет UUID в подписанный список Access API; Paper подхватывает его не
   позднее чем через 15 секунд;
4. для нового аккаунта печатает одноразовый код `/claim`.

Код `/claim` необходимо передать покупателю приватно. Его нельзя публиковать в
общем чате: именно он доказывает, что Discord принадлежит владельцу выданной
проходки. Повторный `grant` аннулирует предыдущий неиспользованный код.

Дополнительные команды:

- `/springauth status <ник>` — состояние проходки и UUID;
- `/springauth revoke <ник>` — отзыв и немедленное отключение;
- `/springauth sync <ник>` — проверка состояния в API; Paper синхронизируется автоматически.

## Первый вход игрока

1. Игрок получает у администратора код и выполняет в Discord
   `/claim XXXX-XXXX-XXXX`.
2. Бот привязывает Discord, выдаёт роль и синхронизирует ник.
3. Игрок подключается с выданным Minecraft-ником через любой лаунчер.
4. Velocity удерживает его в виртуальном Limbo и показывает восьмисимвольный код.
5. Игрок выполняет `/code XXXXXXXX` с уже привязанного Discord.
6. Одноразовое подтверждение потребляется, и это же соединение переходит на
   главный сервер.

Каждое новое соединение требует нового `/code`. Паролей нет. Это
беспарольное подтверждение входа через Discord, а не полноценная двухфакторная
авторизация. В будущем вторым фактором станет WebAuthn/passkey на сайте.

## Защита offline-ников

Ник и вычисленный лаунчером offline UUID не считаются удостоверением личности.
Access API назначает аккаунту постоянный случайный UUID, а Velocity подменяет
профиль до входа на backend. Непривязанный аккаунт нельзя захватить через код
входа: сначала нужен отдельный секрет `/claim`, выданный администратором.

Modern Forwarding подписывает передаваемый профиль, но не заменяет firewall.
Если Velocity и Paper находятся на одном выделенном узле, Paper следует
привязать к `127.0.0.1`. На разных узлах нужен firewall или приватный туннель.

## Файлы и сборка

- исходники и инструкции: `spring-auth/`;
- Velocity JAR: `jar/SpringAuth-Velocity-0.2.0.jar`;
- Paper JAR: `jar/SpringAuth-Paper-0.2.0.jar`;
- примеры конфигов: `spring-auth/config-examples/`;
- полный порядок установки: `spring-auth/docs/deployment.md`;
- протокол API: `spring-auth/docs/protocol.md`.

Для сборки используется `spring-auth/gradlew.bat clean test build`. На главном
сервере Paper-плагин работает в `mode: main`; на Velocity дополнительно нужен
совместимый JAR `jar/limboapi-1.1.27-SNAPSHOT-013034d.jar`. После установки JAR и изменения forwarding требуется полный
перезапуск обоих процессов; `/reload` недостаточно.
