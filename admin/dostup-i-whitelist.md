# Доступ и SpringAuth v2

SpringAuth v2 — действующая серверная авторизация для сети в `offline-mode`.
Она работает с официальными и неофициальными аккаунтами, любыми лаунчерами и
не требует клиентского мода. Старая схема с киком Paper и временной ролью
LuckPerms полностью удалена и не должна возвращаться на сервер.

## Как это работает простыми словами

Проходка, привязка Discord и подтверждение входа — три разные вещи.

**Проходка** отвечает на вопрос «этому Minecraft-аккаунту вообще разрешено
играть?». Администратор создаёт её командой `/springauth grant`. Проходка может
быть временной или постоянной.

**Привязка** отвечает на вопрос «какой Discord владеет этой проходкой?». После
первой выдачи администратор получает секретный код `/claim`. Игрок отправляет
его боту один раз. Угадывание чужого Minecraft-ника не позволяет украсть
аккаунт, потому что без кода `/claim` привязать его нельзя.

**Подтверждение входа** отвечает на вопрос «владелец Discord действительно
разрешает это подключение прямо сейчас?». При каждом соединении игрок ждёт в
Limbo и нажимает кнопку в личном сообщении Discord. Только после этого
Velocity переводит именно это соединение на основной сервер.

Лаунчер в принятии решения не участвует. Он лишь запускает Minecraft с
выбранным ником и подключает к Velocity. Поэтому одинаково работают SpringRP
Launcher, официальный лаунчер и совместимые сторонние лаунчеры.

## Компоненты

- публичный Velocity на `185.9.145.210:32073` принимает игроков и использует
  стандартный offline UUID точного Minecraft-ника;
- виртуальный Limbo внутри Velocity изолирует игрока до подтверждения входа;
- приватный Paper `main` проверяет локальный UUID-список;
- Access API на `springrp.ru/spring-auth/` хранит проходки, привязки и коды;
- Discord-приложение выполняет `/claim`, отправляет кнопку входа, выдаёт Discord-роль и
  синхронизирует ник на Discord-сервере;
- главный Paper получает список разрешённых UUID из API по исходящему HTTPS.

Paper работает с `online-mode=false` и Modern Forwarding. Старый адрес Paper
`5.129.240.121:25567` является backend-адресом и не должен публиковаться как
адрес для игроков. Modern Forwarding не заменяет firewall: на уровне хостинга
нужно разрешить подключение к Paper только от Velocity. RCON системе не нужен.

## Выдача проходки

Команда выполняется в консоли Velocity или доверенным администратором с правом
`springauth.admin`:

```text
/springauth grant <ник> <срок>
```

Примеры сроков: `12h`, `30d`, `4w`, `permanent`. Команда:

1. создаёт или продлевает проходку;
2. сохраняет стандартный offline UUID, который Velocity вычисляет для этого
   точного написания ника;
3. добавляет UUID в подписанный список Access API; Paper подхватывает его в
   течение одного 15-секундного цикла;
4. для нового аккаунта печатает одноразовый код `/claim`.

Код `/claim` необходимо передать покупателю приватно. Его нельзя публиковать в
общем чате: именно он доказывает, что Discord принадлежит владельцу выданной
проходки. Повторный `grant` аннулирует предыдущий неиспользованный код.

Дополнительные команды:

- `/springauth status <ник>` — состояние проходки и UUID;
- `/springauth revoke <ник>` — отзыв и немедленное отключение;
- `/springauth sync <ник>` — проверка состояния в API; Paper синхронизируется автоматически.

## Первый вход игрока

1. Игрок получает у администратора код и выполняет в Discord
   `/claim XXXX-XXXX-XXXX`.
2. Бот привязывает Discord, выдаёт роль и синхронизирует ник.
3. Игрок подключается с выданным Minecraft-ником через любой лаунчер.
4. Velocity удерживает его в виртуальном Limbo, а бот отправляет сообщение привязанному Discord.
5. Игрок нажимает **Подтвердить вход** в личном сообщении бота.
6. Одноразовое подтверждение потребляется, и это же соединение переходит на
   главный сервер.

Кнопка **Отклонить вход** переводит попытку в конечное состояние `denied`,
после чего Velocity отключает соответствующего игрока из Limbo.

Каждое новое соединение требует новой кнопки. Она ограничена по времени,
связана с одним конкретным соединением и после успешного входа повторно не
используется. Паролей нет. Это беспарольное подтверждение через Discord, а не
полноценная двухфакторная авторизация. В будущем вторым фактором может стать
WebAuthn/passkey на сайте.

## Что хранится

Access API хранит Minecraft-ник, соответствующий offline UUID, Discord ID,
состояние и срок проходки. Исходный `/claim` не хранится: сохраняется только
его SHA-256-хеш. Попытки входа живут недолго и погашаются после использования.

Paper получает только актуальный список разрешённых UUID и сохраняет последний
успешно проверенный снимок локально. Если API временно недоступен, это не
превращается в автоматическую выдачу доступа новым игрокам.

## Отзыв и окончание срока

`/springauth revoke <ник>` отзывает проходку. После синхронизации UUID исчезает
из списка Paper, а новые подключения перестают проходить. Истёкшая проходка
ведёт себя так же. Discord-роль является удобным отображением статуса, но не
заменяет серверную проверку Access API.

## Защита offline-ников

Ник и offline UUID не считаются удостоверением личности: их может вычислить
кто угодно. Защиту дают отдельный секрет `/claim`, привязанный Discord и новая
приватная кнопка для каждого соединения. Velocity не отправляет игрока на backend до
успешного подтверждения, а Paper принимает профиль только через подписанный
Modern Forwarding канал.

Modern Forwarding подписывает передаваемый профиль, но не заменяет firewall.
Если Velocity и Paper находятся на одном выделенном узле, Paper следует
привязать к `127.0.0.1`. На разных узлах нужен firewall или приватный туннель.
